It carries the git created/updated facts that Material normally prints at the *bottom* of the page via partials/source-file.html, plus the documented version of the component the page describes. The partial has two modes, and a page reaches it by declaring either key: component: RONL Business API → names one component; shows its version scope: cross-cutting → describes every component at once The second mode exists because pages under docs/en/contributing/ describe the tooling across ALL components simultaneously. Stamping such a page with any single component's version would be false, and picking one of the five arbitrary — but leaving the header off entirely made "no badge" ambiguous between "no version applies here" and "this page has not been synced yet". So the header is present either way, and its right-hand fact says which kind of page you are on. Cross-cutting pages assert the docs_built date instead of a version, since that is the one date that genuinely applies to them: it is when the site was last reconciled against every component at once. See the content block in main.html, which gates on either key and also suppresses the bottom source-file aside so the facts move rather than appear twice. The component version and docs_built date both come from docs/repo-versions.json, loaded into config.extra by hooks/repo_versions.py. Two further facts, each optional: build (component mode) — repo-versions.json may record, per component, the frontend build that was serving the recorded environment: "build 007b350 · #39". It is a different fact from the version: a new build can reach an environment with no release bump, and a reader can compare this string with the one the running application prints. verified (cross-cutting mode) — a page may declare which commit of each component its claims were last re-checked against: verified: date: 2026-09-09 against: CPSV Editor: bbda389 Linked Data Explorer: 007b350 Each SHA links to the commit in the component's ci_repo — GitHub for the three applications — where the deploy runs it triggered are listed. The GitLab mirror carries the same SHAs but shows none of the runs, and lags. The stamp is per page on purpose. A sync re-verifies only the pages it touches, so a site-wide list of current builds would assert verification that never happened. It is keyed on commits, not build ids, because deploy workflows are path-filtered: most of what a contributing page describes (workflows, SECURITY-PIPELINE.md, runner configs) changes without producing a new frontend build at all. A component appears only if its claims on that page were re-checked on that date. /iou-document-patch writes the stamp and checks it for staleness; nothing here does, so the build stays offline. -#} {#- An archived page describes an older release on purpose, and says so in its own banner.
